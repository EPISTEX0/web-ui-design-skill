backoff-kit

Retry async calls with exponential backoff and jitter. Small, dependency-free, written in TypeScript.

TypeScript zero dependencies AbortSignal support

Install

shell 
npm install backoff-kit

Also works with pnpm add backoff-kit and yarn add backoff-kit. Types ship with the package.

Quick start

Wrap any function that returns a promise. If it rejects, retry waits and calls it again, with a longer wait each time.

ts 
import { retry } from "backoff-kit";

const user = await retry(
  () => fetchUser("42"),
  { retries: 5, minDelay: 200 }
);

This makes one initial attempt and up to 5 retries. If every attempt fails, the promise rejects with the last error.

How delays work

Before retry number n (starting at 0), the base delay is min(maxDelay, minDelay × factorn). Jitter then randomizes that value so many clients don't retry in lockstep. Try the numbers below.

Grey = base delay before jitter. Orange = a sample delay after jitter.

retry(fn, options)

ts 
function retry<T>(
  fn: (attempt: number) => Promise<T> | T,
  options?: RetryOptions
): Promise<T>;
ParameterDescription
fnThe work to attempt. Receives the zero-based attempt number (0 for the first call). May be sync or async.
optionsOptional. See Options. Every field has a default.

Resolves with the value from the first successful attempt. Rejects when retries run out, when shouldRetry returns false, or when signal aborts.

retries

number · default 3

Maximum number of retries after the first attempt. retries: 0 runs fn once with no retry.

minDelay

number, ms · default 100

Base delay before the first retry. Later delays grow from this value.

maxDelay

number, ms · default 10000

Upper bound on the base delay. Without a cap, exponential growth gets very large after a few attempts.

factor

number · default 2

Multiplier applied per retry. 2 doubles the delay each time; 1 gives a constant delay.

jitter

"full" | "equal" | "none" · default "full"

"full" picks a random delay between 0 and the base delay. "equal" keeps half the base delay and randomizes the other half. "none" uses the base delay as is, which is useful in tests.

shouldRetry

(error, attempt) => boolean | Promise<boolean> · default: always retry

Called after each failure. Return false to stop and reject with that error immediately. Use it to avoid retrying errors that can never succeed, such as a 400 or 404.

onRetry

(error, attempt, delay) => void · default none

Called just before waiting, once per scheduled retry. delay is the final wait in ms, after jitter. Good for logging and metrics.

signal

AbortSignal · default none

Cancels pending waits and prevents further attempts. See Aborting.

Errors

  • Retries exhausted: rejects with the error from the last attempt, unchanged.
  • shouldRetry returned false: rejects with the error that attempt threw.
  • Aborted: rejects with signal.reason (a DOMException named AbortError by default).

Recipe: HTTP 429 handling

Retry rate limits and transient server errors, but fail fast on client errors. Honor the server's Retry-After header when present by waiting before the call is retried.

ts 
import { retry } from "backoff-kit";

class HttpError extends Error {
  constructor(public status: number, public retryAfterMs?: number) {
    super(`HTTP ${status}`);
  }
}

async function getJson(url: string) {
  const res = await fetch(url);
  if (!res.ok) {
    const header = res.headers.get("retry-after");
    throw new HttpError(res.status, header ? Number(header) * 1000 : undefined);
  }
  return res.json();
}

const data = await retry(() => getJson("https://api.example.com/items"), {
  retries: 6,
  minDelay: 500,
  shouldRetry: async (err) => {
    if (!(err instanceof HttpError)) return true;   // network failure
    if (err.retryAfterMs) await sleep(err.retryAfterMs);  // honor Retry-After
    return err.status === 429 || err.status >= 500;
  },
  onRetry: (err, attempt, delay) =>
    console.warn(`retry #${attempt + 1} in ${Math.round(delay)}ms`),
});

const sleep = (ms: number) => new Promise((r) => setTimeout(r, ms));
Because the Retry-After wait happens inside shouldRetry, the normal backoff delay is added on top of it. That's safe for rate limits: you never retry earlier than the server asked.

Recipe: aborting with AbortSignal

Pass a signal to cancel from outside, for example on a timeout or when a user navigates away. Abort also interrupts a delay that is already in progress.

ts 
const controller = new AbortController();
setTimeout(() => controller.abort(), 8000);   // give up after 8s

try {
  await retry(() => ping(), { retries: 20, signal: controller.signal });
} catch (err) {
  if ((err as Error).name === "AbortError") console.log("cancelled");
  else throw err;
}

// Or use the built-in timeout helper:
await retry(() => ping(), { signal: AbortSignal.timeout(8000) });

To cancel the in-flight request too, forward the signal into your own call. fn doesn't receive it automatically, so close over the same signal: retry(() => fetch(url, { signal }), { signal }).

Recipe: custom retry predicates

Decide per error whether another attempt is worthwhile. Stop on permanent failures, retry on transient ones, and cap by attempt number if you want a stricter rule than retries.

ts 
const TRANSIENT = new Set(["ECONNRESET", "ETIMEDOUT", "EAI_AGAIN"]);

await retry(() => db.query(sql), {
  retries: 10,
  shouldRetry: (err: any, attempt) => {
    if (err?.code && !TRANSIENT.has(err.code)) return false;  // permanent
    if (err?.name === "ValidationError")     return false;  // bad input
    return attempt < 4;                                   // stricter cap
  },
});
