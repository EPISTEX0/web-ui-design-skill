backoff-kit

Retry async calls with exponential backoff and jitter. One function, no dependencies, written in TypeScript.

Flaky networks, rate limits and cold databases fail in ways that clear up on their own. retry calls your function again after a growing, randomized pause, and stops when it succeeds, runs out of attempts, or is aborted.

Install

npm install backoff-kit
pnpm add backoff-kit
yarn add backoff-kit

Types ship with the package. It runs anywhere that has Promise, setTimeout and AbortSignal: Node 18+, Deno, Bun and current browsers.

Quick start

Wrap the call that might fail. If it throws or rejects, retry waits and tries again, up to 5 retries by default.

fetch-user.ts
import { retry } from "backoff-kit";

const user = await retry(async () => {
  const res = await fetch("https://api.example.com/users/42");
  if (!res.ok) throw new Error(`HTTP ${res.status}`);
  return res.json();
});

Tune the schedule by passing options as the second argument:

With options
const rows = await retry(() => db.query("select * from jobs"), {
  retries: 3,
  minDelay: 200,
  maxDelay: 5_000,
  onRetry: ({ attempt, delay, error }) => {
    console.warn(`attempt ${attempt} failed, retrying in ${delay} ms`, error);
  },
});

retry(fn, options)

Signature
function retry<T>(
  fn: (attempt: number) => Promise<T> | T,
  options?: RetryOptions,
): Promise<T>;

fn receives the attempt number, starting at 1. The returned promise resolves with the value of the first successful call. If every attempt fails, it rejects with the error from the last one. See Errors.

Options

Every option is optional. Delays are in milliseconds.

retries

number · default 5

How many times to retry after the first attempt fails. retries: 5 means at most 6 calls to fn. Use 0 to disable retrying, and Infinity to retry until aborted.

minDelay

number · default 100

The base delay before the first retry, before jitter is applied.

maxDelay

number · default 30000

Upper bound on any single delay. Growth stops here, so a long retry run settles into a steady pace instead of waiting minutes.

factor

number · default 2

The multiplier applied to the delay after each failed attempt. With minDelay: 100 and factor: 2 the base delays are 100, 200, 400, 800 and so on.

jitter

"full" | "equal" | "none" · default "full"

How much randomness to add, so clients that failed together don't all retry together.

"full" waits a random time between 0 and the base delay. "equal" waits half the base delay plus a random amount up to the other half. "none" waits exactly the base delay, which is useful in tests.

signal

AbortSignal · default undefined

Cancels the whole operation. Aborting during a wait ends it immediately. Aborting after an attempt has started is up to fn, so pass the same signal to your own request. See Aborting with AbortSignal.

shouldRetry

(error: unknown, attempt: number) => boolean | number | Promise<boolean | number> · default always true

Decides whether a failure is worth retrying. Return false to stop and reject with that error. Return true to use the normal schedule. Return a number to wait exactly that many milliseconds instead, still capped by maxDelay. See Custom retry predicates.

onRetry

(info: { error: unknown; attempt: number; delay: number }) => void · default undefined

Called after a failed attempt that will be retried, just before the wait begins. attempt is the one that just failed and delay is the wait about to happen. Use it for logging and metrics. It is not called for the final failure.

    Errors

    When retries are used up, or shouldRetry returns false, the promise rejects with the original error from the last attempt. Nothing is wrapped, so instanceof checks and your own error fields keep working.

    When signal aborts, the promise rejects with signal.reason, which is a DOMException named AbortError unless you passed your own reason to abort().

    Telling the cases apart
    try {
  await retry(callApi, { signal });
} catch (err) {
  if (signal.aborted) {
    // cancelled by the caller
  } else {
    // out of retries, or shouldRetry said stop
  }
}

    HTTP 429 handling

    A 429 Too Many Requests response often carries a Retry-After header saying how long to wait. Honor it by returning that wait from shouldRetry, and fall back to the normal schedule when the header is missing.

    rate-limited.ts
    class HttpError extends Error {
  constructor(readonly status: number, readonly retryAfter?: string | null) {
    super(`HTTP ${status}`);
  }
}

function retryAfterMs(value?: string | null): number | undefined {
  if (!value) return undefined;
  const seconds = Number(value);
  if (Number.isFinite(seconds)) return seconds * 1000;
  const date = Date.parse(value); // HTTP-date form
  return Number.isNaN(date) ? undefined : Math.max(0, date - Date.now());
}

const data = await retry(
  async () => {
    const res = await fetch(url);
    if (!res.ok) throw new HttpError(res.status, res.headers.get("retry-after"));
    return res.json();
  },
  {
    retries: 6,
    maxDelay: 60_000,
    shouldRetry: (err) => {
      if (!(err instanceof HttpError)) return true;           // network error
      if (err.status === 429) return retryAfterMs(err.retryAfter) ?? true;
      return err.status >= 500;                               // retry 5xx, not 4xx
    },
  },
);

    Keep maxDelay at or above the longest Retry-After you are willing to honor. A server asking for 30 seconds is cut to maxDelay if that is lower.

    Aborting with AbortSignal

    Pass a signal to cancel retrying from outside, for example when a user navigates away or a request times out. Forward the same signal to fetch so an attempt in flight is cancelled too.

    Cancel from a button
    const controller = new AbortController();
cancelButton.onclick = () => controller.abort();

try {
  const data = await retry(
    () => fetch(url, { signal: controller.signal }).then((r) => r.json()),
    { signal: controller.signal },
  );
  render(data);
} catch (err) {
  if (controller.signal.aborted) return; // user cancelled, nothing to show
  showError(err);
}

    Setting an overall deadline

    AbortSignal.timeout() caps the total time across all attempts and waits.

    Give up after 10 seconds
    const signal = AbortSignal.timeout(10_000);

await retry(() => fetch(url, { signal }), { signal, retries: Infinity });

    If the signal is already aborted when you call retry, fn is never called and the promise rejects at once.

    Custom retry predicates

    By default every thrown error is retried. That is wrong for failures that will never succeed, such as a validation error or a missing record. Use shouldRetry to separate those out.

    Retry only transient failures
    const TRANSIENT = new Set(["ECONNRESET", "ETIMEDOUT", "EAI_AGAIN"]);

await retry(() => client.send(message), {
  shouldRetry: (err) =>
    err instanceof Error && "code" in err && TRANSIENT.has(String(err.code)),
});

    The predicate also gets the attempt number and may be async, so it can consult other state.

    Stop early, and ask a circuit breaker
    await retry(() => callPayments(order), {
  shouldRetry: async (err, attempt) => {
    if (attempt >= 3 && err instanceof TimeoutError) return false;
    return !(await breaker.isOpen());
  },
});

    If the predicate itself throws, retry rejects with that error.
