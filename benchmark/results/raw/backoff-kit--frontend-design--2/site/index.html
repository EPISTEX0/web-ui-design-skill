backoff-kit

Retry async calls with exponential backoff and jitter. Small, dependency-free, and written in TypeScript.

TypeScript zero dependencies ESM + CJS Node & browsers

Install

npm install backoff-kit

Types ship with the package; there's nothing extra to install. It needs a runtime with Promise and AbortSignal (Node 16+ and all current browsers).

Quick start

Wrap any function that returns a promise. If it rejects, retry waits and calls it again, up to the retry limit.

import { retry } from "backoff-kit";

const user = await retry(
  async () => {
    const res = await fetch("https://api.example.com/users/42");
    if (!res.ok) throw new Error(`HTTP ${res.status}`);
    return res.json();
  },
  { retries: 5, minDelay: 200, maxDelay: 10_000 },
);

With no options, retry makes up to 4 attempts (1 call + 3 retries) with full jitter between 250 ms and 30 s.

Try the delay schedule

Each bar is the maximum wait before that retry; with jitter on, the real wait is a random value up to the bar.

API

function retry<T>(
  fn: (attempt: number) => Promise<T> | T,
  options?: RetryOptions,
): Promise<T>;

fn is called with the attempt number, starting at 1. If it resolves, retry resolves with that value. If it rejects and the error is retryable, retry sleeps and calls fn again. When retries run out, or an error isn't retryable, the promise rejects with the last error.

retries

number · default 3

How many times to retry after the first attempt fails. retries: 3 means at most 4 calls to fn. Use 0 to disable retrying, or Infinity to retry until success (pair it with signal).

minDelay

number, milliseconds · default 250

The base delay, used before the first retry. Later delays grow from this value.

maxDelay

number, milliseconds · default 30000

Upper bound for any single wait, applied before jitter. Keeps long retry chains from sleeping for minutes.

factor

number · default 2

The growth multiplier. The ceiling for retry n is minDelay × factor^(n−1). Use 1 for a constant interval.

jitter

"full" | "equal" | "none" · default "full"

Randomises each wait so many clients that failed together don't all retry at the same instant.

  • "full": random value between 0 and the ceiling. Best at spreading load.
  • "equal": half the ceiling plus a random value up to half. Keeps a minimum wait.
  • "none": always the ceiling. Predictable, which is handy in tests.

shouldRetry

(error: unknown, attempt: number) => boolean | number | Promise<boolean | number>

Decides whether a failure is worth retrying. Return false to stop and reject immediately with that error. Return true to use the computed backoff. Return a number to retry after exactly that many milliseconds, overriding the computed delay (useful for Retry-After). A returned delay still counts against retries but is not clamped by maxDelay. Can be async.

onRetry

(info: { error: unknown; attempt: number; delay: number }) => void

Called after a failure is judged retryable and before the wait starts. attempt is the attempt that just failed; delay is the wait in ms. Intended for logging and metrics. If it throws, that error is surfaced instead of retrying.

signal

AbortSignal

Cancels the whole operation. Aborting during a wait ends the wait immediately and rejects with the signal's reason; an already-aborted signal rejects before the first call. The signal is not passed to fn automatically, so pass it to fetch yourself if you want in-flight work cancelled. See the recipe.

Errors

When attempts are exhausted, retry rejects with the last error thrown by fn, unchanged, so your existing catch and instanceof checks keep working. When aborted, it rejects with signal.reason (a DOMException named AbortError by default).

How delays work

// n = 1 for the first retry
ceiling = min(maxDelay, minDelay * factor ** (n - 1))

full:  delay = random(0, ceiling)
equal: delay = ceiling / 2 + random(0, ceiling / 2)
none:  delay = ceiling

With the defaults and jitter: "none", the ceilings are 250, 500, 1000, 2000 … ms, capped at 30 s.

Recipe: HTTP 429 handling

Retry on rate limiting and transient server errors, and honour the server's Retry-After header when present. Returning a number from shouldRetry overrides the computed backoff.

import { retry } from "backoff-kit";

class HttpError extends Error {
  constructor(readonly status: number, readonly retryAfter?: string | null) {
    super(`HTTP ${status}`);
  }
}

function retryAfterMs(value?: string | null): number | undefined {
  if (!value) return;
  const secs = Number(value);
  if (Number.isFinite(secs)) return secs * 1000;
  const date = Date.parse(value);           // HTTP-date form
  return Number.isNaN(date) ? undefined : Math.max(0, date - Date.now());
}

const data = await retry(
  async () => {
    const res = await fetch("https://api.example.com/reports");
    if (!res.ok) throw new HttpError(res.status, res.headers.get("retry-after"));
    return res.json();
  },
  {
    retries: 6,
    shouldRetry: (err) => {
      if (!(err instanceof HttpError)) return true;       // network failure
      if (err.status === 429) return retryAfterMs(err.retryAfter) ?? true;
      return err.status >= 500;                            // retry 5xx, not other 4xx
    },
    onRetry: ({ attempt, delay }) =>
      console.warn(`attempt ${attempt} failed, retrying in ${Math.round(delay)}ms`),
  },
);
Cap the server-provided wait yourself if you can't tolerate a long pause: Math.min(retryAfterMs(…) ?? 0, 60_000).

Recipe: aborting with AbortSignal

Give the whole operation a deadline, or let a user cancel it. Pass the same signal to fetch so an in-flight request is cancelled too.

const controller = new AbortController();
cancelButton.onclick = () => controller.abort();

// or a hard deadline for all attempts combined:
// const signal = AbortSignal.timeout(30_000);

try {
  const res = await retry(
    () => fetch("/api/export", { signal: controller.signal }).then((r) => {
      if (!r.ok) throw new Error(`HTTP ${r.status}`);
      return r;
    }),
    { retries: Infinity, signal: controller.signal },
  );
} catch (err) {
  if (controller.signal.aborted) {
    // cancelled by the user or timed out; not a real failure
    return;
  }
  throw err;
}

Check signal.aborted rather than the error type: an aborted fetch and an aborted retry both reject, but with different error objects.

Recipe: custom retry predicates

Only retry what can plausibly succeed next time. Retrying a validation error or a bad password just wastes time and load.

const TRANSIENT = new Set(["ECONNRESET", "ETIMEDOUT", "EAI_AGAIN", "ECONNREFUSED"]);

await retry(() => db.query(sql), {
  retries: 4,
  shouldRetry: (err, attempt) => {
    const code = (err as NodeJS.ErrnoException).code;
    if (code && TRANSIENT.has(code)) return true;
    if (code === "40001") return attempt < 3;   // serialization failure: fewer tries
    return false;                                // syntax errors, constraint violations…
  },
});

The predicate can be async, which is useful for checking something external, such as whether a circuit breaker is open:

await retry(callPartner, {
  shouldRetry: async (err) => !(await breaker.isOpen()) && isTransient(err),
});
