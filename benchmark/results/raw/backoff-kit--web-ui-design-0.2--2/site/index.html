backoff-kit

A small TypeScript library that retries a failing async call, waiting longer after each failure and adding randomness so many clients don't retry in lockstep.

  • One function, retry(fn, options), with typed options and no runtime dependencies.
  • Cancel mid-wait with an AbortSignal.
  • Decide per error whether to retry, and honor server hints such as Retry-After.

Install

npm install backoff-kit

Types are bundled. Use it in any runtime that has Promise, setTimeout and AbortSignal: Node, Deno, Bun and browsers.

import
import { retry } from 'backoff-kit'

Quick start

Wrap the call in a function and pass it to retry. If the function throws or rejects, retry waits and calls it again. When it resolves, you get its value.

fetch-user.ts
import { retry } from 'backoff-kit'

const user = await retry(async () => {
  const res = await fetch('/api/user')
  if (!res.ok) throw new Error(`HTTP ${res.status}`)
  return res.json()
})

With no options, it makes up to 6 calls (the first plus 5 retries), starting at 200 ms and doubling each time, with full jitter. If every call fails, retry rejects with the last error.

With options
const data = await retry(() => loadReport(), {
  retries: 3,
  minDelay: 500,
  maxDelay: 10_000,
  onRetry: (err, attempt, delay) => {
    console.warn(`attempt ${attempt} failed`, err)
    console.warn(`retrying in ${delay} ms`)
  },
})

How delays work

Before retry n, the ceiling is min(maxDelay, minDelay × factor^(n−1)). The jitter mode then picks the actual wait at or below that ceiling. Change the options to see the range each retry can wait.

    API reference

    Signature
    function retry<T>(
  fn: (attempt: number, signal?: AbortSignal)
    => Promise<T> | T,
  options?: RetryOptions,
): Promise<T>
    • fn receives the attempt number (starting at 1) and the signal you passed in options, so you can forward it to fetch.
    • Resolves with the value of the first successful call.
    • Rejects with the last error once retries run out or shouldRetry returns false.
    • Rejects with signal.reason if the signal aborts, including while waiting between attempts.

    Options

    Every option is optional.

    retries
    Type numberDefault 5

    How many times to retry after the first call fails. 0 makes a single attempt.

    minDelay
    Type number (ms)Default 200

    The delay ceiling before the first retry.

    maxDelay
    Type number (ms)Default 30_000

    Upper limit for any wait, including values returned by retryAfter.

    factor
    Type numberDefault 2

    Multiplier applied to the ceiling after each retry. Use 1 for a constant delay.

    jitter
    Type 'full' | 'equal' | 'none'Default 'full'

    'full' waits a random time between 0 and the ceiling. 'equal' waits half the ceiling plus a random share of the other half. 'none' waits exactly the ceiling.

    signal
    Type AbortSignalDefault none

    Aborting stops the current wait and rejects with signal.reason. If the signal is already aborted, fn is never called. See Aborting.

    shouldRetry
    Type (error, attempt) => boolean | Promise<boolean>Default retries every error

    Called after each failure. Return false to stop and reject with that error. attempt is the number of the call that just failed.

    retryAfter
    Type (error, attempt) => number | undefinedDefault none

    Return a delay in milliseconds to use instead of the computed one, for example from a Retry-After header. Return undefined to fall back to the schedule. The result is capped at maxDelay and is not jittered.

    onRetry
    Type (error, attempt, delay) => voidDefault none

    Called just before each wait, with the error, the attempt that failed and the chosen delay in milliseconds. Use it for logging and metrics.

    Recipes

    Handle HTTP 429 and Retry-After

    Throw an error that carries the response, retry only on rate limits and server errors, and let the server's Retry-After header set the wait.

    rate-limited.ts
    class HttpError extends Error {
  constructor(public res: Response) {
    super(`HTTP ${res.status}`)
  }
}

const data = await retry(
  async () => {
    const res = await fetch(url)
    if (!res.ok) throw new HttpError(res)
    return res.json()
  },
  {
    retries: 6,
    shouldRetry: (err) =>
      err instanceof HttpError &&
      (err.res.status === 429 || err.res.status >= 500),
    retryAfter: (err) => {
      if (!(err instanceof HttpError)) return
      const secs = Number(err.res.headers.get('retry-after'))
      return Number.isFinite(secs) ? secs * 1000 : undefined
    },
  },
)

    Retry-After can also be an HTTP date. Number() returns NaN for that form, so the schedule takes over. Parse the date yourself if your API uses it.

    Abort with AbortSignal

    Pass a signal to stop retrying from outside, for example on a timeout or when the user navigates away. Forward the same signal to fetch so an in-flight request is cancelled too.

    abort.ts
    const ctrl = new AbortController()
const timer = setTimeout(() => ctrl.abort(), 15_000)

try {
  const data = await retry(
    (attempt, signal) =>
      fetch(url, { signal }).then((r) => r.json()),
    { signal: ctrl.signal },
  )
  render(data)
} catch (err) {
  if (ctrl.signal.aborted) {
    console.log('gave up after 15 s')
  } else {
    throw err
  }
} finally {
  clearTimeout(timer)
}

    To use the built-in timeout signal, pass AbortSignal.timeout(15_000) as signal instead of creating a controller.

    Custom retry predicates

    shouldRetry may be async and sees the attempt number. This one retries only timeouts, rate limits and server errors, and gives network failures (which surface as a TypeError from fetch) just two retries.

    predicate.ts
    const RETRYABLE = new Set([408, 425, 429, 500, 502, 503, 504])

await retry(() => callApi(), {
  shouldRetry: async (err, attempt) => {
    const status = (err as { status?: number }).status
    if (status !== undefined) {
      return RETRYABLE.has(status)
    }
    if (err instanceof TypeError) {
      return attempt <= 2
    }
    return false
  },
})

    Errors you don't list are thrown straight away, so bugs such as a 400 from bad input are not retried.
