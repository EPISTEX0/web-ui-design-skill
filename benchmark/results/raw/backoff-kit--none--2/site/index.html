backoff-kit

A small TypeScript library for retrying async calls with exponential backoff and jitter. Zero dependencies, fully typed, works in Node and the browser.

TypeScript Zero dependencies ESM + CJS Open source

Install

npm install backoff-kit
pnpm add backoff-kit
yarn add backoff-kit
bun add backoff-kit

Types ship with the package; no @types install is needed.

Quick start

Wrap any function that returns a promise. If it rejects, retry waits and calls it again, up to the configured number of retries.

import { retry } from "backoff-kit";

const user = await retry(async () => {
  const res = await fetch("https://api.example.com/users/42");
  if (!res.ok) throw new Error(`HTTP ${res.status}`);
  return res.json();
});

console.log(user);

With no options, this makes up to 6 calls (1 initial + 5 retries), waiting roughly 100 ms, 200 ms, 400 ms… between attempts with full jitter, capped at 30 s. If every attempt fails, the last error is thrown.

Try the delay schedule

This widget uses the same formula described below so you can see how the options shape the waits.

retry(fn, options)

function retry<T>(
  fn: (attempt: number) => Promise<T> | T,
  options?: RetryOptions,
): Promise<T>;
fnThe work to attempt. Receives the 1-based attempt number. May be sync or async; a thrown error or rejected promise counts as a failure.
optionsOptional RetryOptions.
returnsA promise that resolves with the first successful result of fn, or rejects with the final error once retries are exhausted, shouldRetry declines, or the signal aborts.

Options

retries

number · default 5

Maximum number of retries after the first call, so the total number of calls is retries + 1. Use 0 to disable retrying while keeping the other behavior (abort, hooks).

minDelay

number, milliseconds · default 100

The base delay before the first retry. It is the starting point that factor grows from.

maxDelay

number, milliseconds · default 30000

Upper bound on any single wait. The exponential growth is clamped to this value before jitter is applied.

factor

number · default 2

Multiplier applied for each successive retry. A factor of 1 gives a constant delay.

jitter

"full" | "equal" | "none" · default "full"

Randomization that spreads out clients so they don't retry in lockstep.

  • "full": wait a random time between 0 and the capped delay. Best for reducing contention.
  • "equal": wait half the capped delay plus a random amount up to the other half. Keeps a guaranteed minimum wait.
  • "none": wait exactly the capped delay. Predictable, mainly useful in tests.

signal

AbortSignal · default none

Cancels the operation. Aborting during a wait ends it immediately; aborting before an attempt prevents it. The returned promise rejects with the signal's reason. See the recipe.

shouldRetry

(error: unknown, attempt: number) => boolean | Promise<boolean> · default retry everything

Called after each failure. Return false to stop and reject with that error right away. attempt is the 1-based number of the attempt that just failed. See the recipe.

retryAfter

(error: unknown) => number | undefined · default none

Return a number of milliseconds to use as the wait instead of the computed backoff, for example from a Retry-After header. Return undefined to fall back to the computed delay. The value is still clamped to maxDelay.

onRetry

(error: unknown, attempt: number, delayMs: number) => void · default none

Called just before waiting for a retry. Useful for logging and metrics. It is not called for the final failure.

How delays are computed

For retry number n (starting at 0), the capped delay is:

capped = min(maxDelay, minDelay * factor ** n)

full  : random(0, capped)
equal : capped / 2 + random(0, capped / 2)
none  : capped

With the defaults, the capped delays are 100, 200, 400, 800 and 1600 ms.

Errors

retry rejects with the original error from the last attempt; it is not wrapped. When the signal aborts, it rejects with signal.reason (a DOMException named AbortError by default).

Recipes

HTTP 429 handling

Retry rate-limit and transient server responses, and respect the server's Retry-After header when it sends one. Other 4xx errors are not worth retrying.

import { retry } from "backoff-kit";

class HttpError extends Error {
  constructor(readonly status: number, readonly headers: Headers) {
    super(`HTTP ${status}`);
  }
}

function retryAfterMs(headers: Headers): number | undefined {
  const value = headers.get("retry-after");
  if (!value) return undefined;
  const seconds = Number(value);
  if (!Number.isNaN(seconds)) return seconds * 1000;
  const date = Date.parse(value);            // HTTP-date form
  return Number.isNaN(date) ? undefined : Math.max(0, date - Date.now());
}

const data = await retry(
  async () => {
    const res = await fetch("https://api.example.com/items");
    if (!res.ok) throw new HttpError(res.status, res.headers);
    return res.json();
  },
  {
    retries: 6,
    minDelay: 500,
    maxDelay: 60_000,
    shouldRetry: (err) =>
      err instanceof HttpError && [429, 502, 503, 504].includes(err.status),
    retryAfter: (err) =>
      err instanceof HttpError ? retryAfterMs(err.headers) : undefined,
    onRetry: (err, attempt, delay) =>
      console.warn(`attempt ${attempt} failed (${err}); retrying in ${delay} ms`),
  },
);

Aborting with AbortSignal

Pass a signal to stop retrying when the user navigates away, a request is cancelled, or an overall deadline passes. Pass the same signal to fetch so an in-flight request is cancelled too.

import { retry } from "backoff-kit";

const controller = new AbortController();
document.querySelector("#cancel")!.addEventListener("click", () => controller.abort());

try {
  const result = await retry(
    () => fetch("/api/report", { signal: controller.signal }).then((r) => r.json()),
    { signal: controller.signal, retries: 10 },
  );
} catch (err) {
  if (err instanceof DOMException && err.name === "AbortError") {
    console.log("cancelled");
  } else {
    throw err;
  }
}

For an overall time limit, use AbortSignal.timeout:

await retry(callApi, { signal: AbortSignal.timeout(15_000) });

Custom retry predicates

shouldRetry decides which failures are transient. Permanent errors such as validation failures should fail immediately instead of burning through retries.

import { retry } from "backoff-kit";

const TRANSIENT = new Set(["ECONNRESET", "ETIMEDOUT", "EAI_AGAIN"]);

const rows = await retry(() => db.query("select * from orders"), {
  shouldRetry: (err, attempt) => {
    if (attempt >= 4) return false;                       // own cap, tighter than retries
    const code = (err as { code?: string }).code;
    return code !== undefined && TRANSIENT.has(code);  // never retry bad SQL, etc.
  },
});

shouldRetry may also be async, for example to check whether a circuit breaker is open before trying again.
